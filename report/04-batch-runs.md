# 4. Задание 3. Пакетные прогоны: горизонт 3600 с, прогрев, CSV, временной ряд

Эта часть описывает инструмент, на котором строятся задания 3–6: расширенный `batch_runs.py`. Выбор длины прогрева `W`, доверительные интервалы парной разности и число прогонов `n` рассматриваются в следующих подразделах задания.

## Что изменено

- **Горизонт.** `--seconds` принимает 60–3600 с (раньше 60–900). Ограничения журнала спроса (`deque(maxlen=900)` в `simulation.py`) снимаются для пакетных прогонов, иначе при `T = 3600` в журнале оставались бы только последние 900 из ~4600 автомобилей.
- **Прогрев применяется ко всем показателям.** Раньше `generated`, `completed`, `delay`, `flow` и `conflicts` брались с начала опыта, и только очередь — после `W`. Теперь на `t = W` фиксируются значения счётчиков модели, а в результат попадают их приращения на `[W, T]`:

  | Показатель | Определение на `[W, T]` |
  | --- | --- |
  | `generated`, `completed`, `conflicts` | значение на `T` минус значение на `W` |
  | `delay_completed_sec` | `(Σ задержек завершивших на T − на W) / completed`; учитывается вся задержка автомобиля, в том числе набранная до `W` |
  | `flow_completed_per_hour` | `completed · 3600 / (T − W)` |
  | `mean_queue_after_warmup`, `max_queue_after_warmup` | по секундным отсчётам очереди `t = W, …, T` |
  | `final_queue` | отсчёт `t = T` |
  | `remaining` | `generated − completed` на интервале, как в контракте |

  `remaining` на интервале с прогревом может быть отрицательным (в контрольной серии от −12 до +12): завершаются и автомобили, появившиеся до `W`. Это не число машин в системе к моменту `T`; для него есть `final_queue` и, когда будет реализована, накопленная задержка.
  Очередь определена как в исходной модели: ожидающие вне схемы плюс автомобили со скоростью ниже 1. Отсчёты берутся каждую секунду по числу шагов модели (20 шагов по 0,05 с), а не через `Simulation.history`, чья метка времени округляется.
- **Параметры плана.** Добавлены `--ew-green` и `--clearance`. Связь `cycle = ns_green + ew_green + 2·clearance` проверяется: из любых двух величин выводится третья, при трёх противоречивых значениях запуск отклоняется. Зелёный любого направления — не менее 6 с. Параметры плана попадают в каждую строку `runs_*.csv` (`cycle, clearance, ns_green, ew_green`).
- **Диапазон SEED.** `--seeds 101-110`, `--seeds 7 17 201-210`, `--seeds 1,5,9-12`; диапазоны включительные, повторы запрещены.
- **Временной ряд очереди.** `--timeseries` пишет `timeseries_<tag>.csv`: `run_id, plan_id, seed, t, queue, queue_N, queue_E, queue_S, queue_W` для `t = 1..T`. Ряд включает прогрев, чтобы по нему можно было выбирать `W`.
- **Файлы серии.** В `results/` создаются `runs_<tag>.csv` (строка на прогон), `summary_<tag>.csv` (строка на план: `n`, среднее, `std`, 95% ДИ по Стьюденту для каждого показателя), по запросу `timeseries_<tag>.csv` и `demand_log_<tag>.csv`. `<tag>` — дата-время или значение `--tag`. Пути можно задать явно: `--out`, `--summary`, `--demand-log`. Столбцы и их порядок соответствуют `CONTRACT.md`; показатели, которые ещё не реализованы (по въездам, накопленная задержка, 95-й процентиль, Уэбстер и т. д.), остаются пустыми.
- **Параллельность.** Пары «план, SEED» выполняются пулом процессов `multiprocessing`; `--workers N` (по умолчанию число ядер). Каждый прогон самодостаточен, поэтому результаты не зависят от `N` и порядка завершения (проверено тестом: `workers=1` и `workers=2` дают идентичные строки). Для сетки задания 4 — `--grid`: `CYCLE` 30–120 с шагом 10 и доля зелёного NS 0,30–0,70 с шагом 0,05 от `CYCLE − 2·CLEARANCE` (90 планов, доля даёт нецелые `NS_GREEN`, например 7,2 с).
- **Функции для скриптов З4–З6.** `evaluate(plan, seeds, *, T=3600, W=300, demand_scale=1.0, options=None, workers=1)` возвращает строки `run_once` по одной на SEED; `evaluate_grid(plans, seeds, ...)` — для набора планов с параллельным запуском. Пример:

  ```python
  from batch_runs import Plan, evaluate
  rows = evaluate(Plan(cycle=60, ns_green=24, ew_green=30, clearance=3), range(201, 211))
  ```

  Скрипты запускаются из корня репозитория: `uv run python -m scripts.<имя>`.
- **Заглушка `run_once` заменена реальным прогоном**, а `run_one` удалён: единственная точка входа — `run_once`/`simulate`. В ходе работы исправлена потеря последней строки в обоих CSV (`writerows(rows[:-1])`).

## Контрольная серия

Базовый план `scenario.py` (`CYCLE=42, NS_GREEN=18, EW_GREEN=18, CLEARANCE=3`), множитель спроса `--demand-scale 1.0` (при этом `scenario.rate_multiplier` по-прежнему даёт 0,95 для варианта команды 2), `T = 3600`, `W = 300`, SEED `101–110` (набор З3 из реестра):

```sh
uv run python batch_runs.py --seconds 3600 --warmup 300 --seeds 101-110 --timeseries
```

Серия из 10 прогонов по 3600 с выполнена за 12 с (10 процессов, по одному на прогон; суммарное процессорное время 115 с, то есть около 12 с на прогон — серийный запуск занял бы около двух минут). Значения по 10 прогонам, среднее и 95% ДИ Стьюдента:

| Показатель на `[300, 3600]` | Среднее | 95% ДИ |
| --- | ---: | ---: |
| Появилось автомобилей | 4582,2 | [4533,2; 4631,2] |
| Завершили поездку | 4582,4 | [4535,3; 4629,5] |
| Средняя суммарная очередь | 10,99 | [10,75; 11,23] |
| Максимальная суммарная очередь | 38,7 | [37,9; 39,5] |
| Задержка завершивших, с | 8,02 | [7,90; 8,14] |
| Поток завершивших, авто/ч | 4999 | [4948; 5050] |
| Конфликты | 918,2 | [888,0; 948,4] |
| Конфликты на 100 завершивших | 20,03 | [19,54; 20,52] |

Средняя по 10 SEED суммарная очередь по блокам 300 с: 10,3; 10,8; 10,9; 11,8; 11,6; 11,0; 11,3; 11,3; 10,4; 11,0; 10,1; 10,9. Очередь растёт в первых блоках и затем колеблется около 11 без монотонного роста до конца прогона. Это наблюдение по сырому ряду; обоснованный выбор `W` по скользящему среднему делается отдельно, и `W = 300` здесь взят как минимум, допустимый заданием.

## Проверки

Тесты (`uv run python -m unittest test_starter.py`) проверяют:

- прогрев: разность `generated` при `W = 0` и `W = 40` равна числу записей журнала с `t_born <= 40`; без прогрева показатели совпадают с итогами самой модели (`generated`, `completed`, `conflicts`, средняя задержка);
- ряд очереди: `t = 1..T`, сумма по въездам равна суммарной очереди, среднее и максимум по отсчётам `t >= W` совпадают со строкой результата, последний отсчёт равен `final_queue`;
- журнал спроса не обрезается при более чем 900 автомобилях;
- разбор плана и SEED, формулу ДИ Стьюдента (`t₀,₉₇₅(9) = 2,2622`), схему `summary_*.csv`;
- CLI: по одной строке на прогон (включая последний), параметры плана в строках, неверные аргументы отклоняются;
- параллельный и последовательный запуск дают одинаковые строки; `evaluate` и `evaluate_grid` сохраняют порядок.

## Ограничения

- Время счёта сильно зависит от плана: при перенасыщении очередь растёт, а модель на каждом шаге обходит все автомобили, поэтому прогон с длинными очередями заметно дороже базового. Полная сетка 90 планов × 10 SEED × 3600 с в этой работе не запускалась; перед перебором стоит замерить время на 1–2 планах и выбрать число прогонов на точку сетки.
- Парные разности, целевая функция и показатели заданий 2, 4–6 в сводку пока не заполняются (поля пусты по контракту).
